# Staging selected upload bases for a room

The private `PhysicalRoomAssetAdoption` coordinator retains explicit upload-base
choices against a genuine seven-family room and creates separate, exact selected
upload stores. Original participant files, native owners and upload stores remain
unchanged. No editor or mutable upload owner is returned. Its `ready` phase means
that local selected clones were checked, not that the operational room has been
replaced or that any server writer may activate.

## Actual source ownership

`capture(root, policy)` returns detached whole upload files and pins for preparing
choices. `begin(root, options)` re-admits the actual root; a snapshot or saved
selection cannot manufacture ownership. Every selected genuine parent is reserved
before authority callbacks. Original/generation upload custody is acquired before
the fresh grant check; the five newer families retain their existing custody.

The source pin includes the exact room intent, catalog selection, participant
families and upload namespaces, current selected document/comment native history
kinds and checkpoint hashes, and complete current upload hashes. The root's
actual retained catalog files and current participants are verified. Whole upload
cuts are captured again after staging work. A stale UI choice cannot be rebound
to a later source cut by changing a diagnostic object.

The existing root/participant policies and the fresh staging grant must both
remain usable. An ended root must be cold-reopened under current explicit host
policies. The independent expired-job history reader keeps its separate contract;
this staging path does not turn that read permission into mutation authority.

Limits come from the root's private policy snapshot, not writable asset-store
facade fields. Each base's complete before-file must match the actual current
upload cut, and its selected union must satisfy both archived and current limits.
All source, catalog, intent and selected destination roles must remain distinct.
Own data fields and dense arrays refuse accessor-selected or sparse choices.

These durable pins cover the selected native lanes and whole uploads. They do
not independently serialize every later live/pending proposal, revision, version
or delivery record. Original recovery custody still retains that work; final
operational adoption must re-admit all those records and their complete historical
references rather than treating this staged pin as whole-room reconciliation.

## Retention before clone creation

The independent `breditor/physical-room-asset-adoption` version-one record uses a
new absent-only IndexedDB schema. Its initial transaction stores the complete
selection and every exact reconciled-base byte before any selected clone is
created. Each base retains both losing whole inputs and its selected union. No
old catalog, asset archive, reconciliation ledger or native protocol changes.

The coordinator owns a real recovery lease for its intent and each selected
destination namespace. Each opened clone also retains actual asset-store custody.
That excludes cooperating writers while asynchronous verification runs. These
leases are origin-local coordination, not account authentication or a cross-device
writer fence.

An ordered participant state moves from `reserved` to `started` to `complete`;
only an all-complete selection can become `ready`. Every transition compares the
actual prior selection and every retained base byte in one transaction. Unknown
or extra fields, changed selections and changed files refuse without repair.

## Interrupted creation and cold retry

A target or phase transaction may commit before its acknowledgement is lost.
Retry reads the actual old or pending successor record, re-admits the saved bases
and current genuine source, and checks existing selected bytes. It does not replay
a phase put or asset insertion merely because the caller observed an error.

An unfinished clone may retain an empty schema after an aborted insertion. Only
the `started`, never-exposed destination can take that retry path. The coordinator
keeps its namespace lease, verifies the existing empty store, closes that handle
and invokes the existing held restore. Its insertion transaction requires empty
storage again, so an intervening foreign row refuses without being overwritten.
No nonempty divergent destination enters this path.

A `complete` destination must already exist and match the exact selected archive.
Missing bytes, a changed queue or a changed budget refuse; a completion marker
does not recreate a database or reseed an empty store. Retained base files remain
available for an explicit new recovery selection.

Blocked and unreturned intent openings retain their actual raw requests for
cleanup retry. Cancellation rejects the public operation even while its raw
request is queued behind foreign work; it does not pretend to cancel or discard
that request. Cleanup remains busy until the actual request drains. A late
upgrade after cancellation or close can only abort, not publish a placeholder.
Closing a returned staging owner needs no continuing grant, waits for actual
custody cleanup and releases its in-memory base/root references after success.
It never closes the caller's original room and never deletes durable data.

## Scope and remaining adoption work

The selection remains bounded to 1,024 participants, a 16 MiB record and 1 GiB of
retained base bytes. A single source-capture pass admits at most 512 MiB of whole
upload archives. Each actual selected store retains its existing, possibly tighter
asset limits. These are refusal bounds, not qualified memory or latency budgets.
The coordinator refuses an oversized whole selection instead of truncating it.

Unselected historical copies remain explicit in `unreconciledParticipants`, even
when the selected local clones are ready. Neither equal actor IDs nor a local
receipt proves registered-stream or current provider coverage.

The [held history and provider reader](ROOM_HISTORY_PROVIDER_CHECK.md) now checks
the original held clients' protected history and whole upload stores against the
actual authenticated native provider, including unreferenced content IDs. It
re-admits stored records and upload bytes after network I/O. This does not admit
the separately staged selected clones, approve their choices or replace the
operational root; those still require the complete selected native/record/upload
basis and durable handoff below.

The next operational contract must combine these staged stores with genuine
native/source ownership, complete current/pending/offline/review/version admission,
all retained-client decisions and current provider byte checks. It must then cross
one verified handoff barrier without discarding either input or weakening the old
participant baseline. Cold staging resume re-admits the named local stored
selection; it does not independently authenticate earlier user approval of that
selection. Operational adoption must bind the exact choices to an independently
trusted selection pin or a fresh explicit decision, not derive approval from a
saved `ready` record. Authenticated activation separately needs the native A/B/C
selection, current control instance, fresh writer registration and stale-writer
fencing. Sustainable history, remaining parity and all thirteen V1 gates remain
required.

## Functional qualification

The [selected qualification](qualification/2026-10-24-room-asset-adoption-staging.json)
passes eighteen normal candidate stages. Source, fresh offline-installed packages
and actual production-bundled code each pass the same 161 laws, with five strict
consumer type fixtures. All 111 prior asset-base/reconciliation laws remain;
the additions are 36 storage laws and fourteen native staging scenarios.

Four new matrix cases cover all seven recovery families across independent
document/comment history pairs. Each execution path cold-reopens 28 original
client instances and 28 selected destinations with exact native/upload checks,
then exercises both future Undo/Redo lanes. Ten further native cases cover lost
phase acknowledgements, absent/changed completed stores, stale choices, occupied
targets, the all-member callback barrier, retained unselected copies and aborted
first insertion. The SDK cases reuse language 3 standard/atomic data; these are
not distinct server registrations or the full native-profile-by-history matrix.
The actual source-matched native producer covers ten profile/wire rooms.

Two separate fresh installed controls preserve their assertions unchanged. The
actual captured pre-repair coordinator fails the aborted-first-insertion case;
the actual captured pre-repair storage module fails both initial/resumed queued
cancellation cases. Fixed packages pass before substitution and after restoration.
The earlier run superseded by the queued-cancellation repair remains retained,
without being counted as final qualification.

The tests use controlled IndexedDB, locks and raster presentation. The normal
Wasm and native producer binary, public-root exports and package versions remain
unchanged. This establishes staged local clones and their recovery, not the final
operational handoff, current provider/stream closure or physical-browser durability.
