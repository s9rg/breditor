# Incoming native history sources

The private incoming-source capture links an admitted local-operation input to
its actual live native source. It supports the distinct `snapshot-v1` and
`flat-local-v1` families without changing their files, schemas, save meanings or
public-root exports. This is a prerequisite for room recovery, not operational
adoption or an authenticated activation grant.

## Incoming provenance and later edits

An imported backup and the source restored from it need not remain the same cut.
The source may have later document edits, comment events and retained versions.
Capture requires the actual source journal's selected incoming file, compared
literally with the admitted archive in bounded byte chunks. An exported file that
was never imported cannot replace that input.

Both incoming LIVE and captured source LIVE are replayed read-only in the
independently selected reader runtime. Native continuation checks cover the
document and comment histories, including their actual history identities;
versions must retain their exact ordered prefix. Source runtime A's native
pointer is never compared inside reader runtime B.

This incoming-provenance relation is deliberately separate from same-point export
equality and arbitrary historical-copy reconciliation. Matching text, writer IDs,
counters or metadata alone proves none of those relationships. Independently
valid captures of divergent copies still require complete room reconciliation;
no branch is selected, merged or discarded by this component.

## Genuine owners and current read policy

Only the actual restored-local or flat-local journal/source pair can create a
capture. The private constructor, runtime owner ledger and exact family checks
refuse copied methods, structural descriptors, old delivery families and
unreturned owners. TypeScript retains nominal archive/capture types and the
source's selection-policy type. No new serialized capability or wire format is
introduced.

The admitted archive handle itself is bound to the capture. Another genuine
archive with identical selections and bytes is not that handle. Reopening a
catalog therefore requires a fresh capture against its actual retained owner.
Disposed archives, changed native/retained-version stamps and revoked read policy
invalidate the capture.

Read permission and native factories are supplied afresh. A writer grant, signal
or execution factory that has ended does not become a read credential or prevent
an independently authorized matching read. Writable or incompatible reader
factories refuse before native execution. Historical local comments remain
local; no relay delivery binding is manufactured.

## Read lifetime and cleanup

Capture holds the real journal read scope. Dispose it before awaiting source
shutdown: the journal waits for held scopes while a retired or closed native
source becomes unreadable. Capture disposal releases that actual borrow and
native-reader registration; it never closes, replaces or recreates the writer.
Cleanup remains possible after revocation or source/archive retirement.

Current policy and the source stamp are checked across asynchronous byte/native
work. Temporary read-only owners are disposed before final owner construction.
Constructed owners remain unavailable until their final checks finish, and read
wrappers are prepared before the last stamp check. A later source change makes
an existing capture stale rather than silently updating its evidence.

The private native-reader contract requires its `check` before and after a
coherent read. The incoming-source normalizer also checks current ownership and
policy. Cached immutable records and an earlier successful check are not new
read permission, persistent readiness or native writer custody.

## Scope of conserved state

Capture does not flush native edits, retry uploads, mutate image providers or
contact a server. Its native records include document/comment checkpoints and
the exact retained-version catalog. The admitted incoming file already retains
its own complete provenance and asset data. Availability of additional LIVE
assets, whole-upload adoption and every historical provider remain separate
room-recovery obligations; a native prefix is not an upload/provider proof.

## Required qualification

Both candidate profiles require the incoming-source contract group, strict type
fence, source probe and fresh installed consumer. The focused native laws cover
both input families and all four history pairs, later LIVE edits, retained-version
staleness, false owners/families, current policy, read-factory rejection, callback
mutation, actual shutdown lifetime and an independently instantiated Wasm reader.

The fixed source/installed probe has forty representative cases: all five normal
native profiles, all four history combinations and both input families. Selection
scopes and capability masks rotate across these cases; this is not their full
Cartesian product. It checks exact source records/versions, unchanged whole
uploads and retained pixels, an ended writer grant with a fresh read grant,
distinct admitted-handle refusal, future native Undo and stale/revoked/disposed
read refusal. The actual production bundle repeats the same workload using
reversible import-location changes only. Synthetic storage does not qualify
physical durability.

The [selected qualification](qualification/2026-10-22-native-input-incoming-source.json)
passes all 33 selected stages from the 339-check functional plan. Source laws
pass 16, including the candidate-plan law; fresh installed packages pass the
same 15 native laws and strict nominal type fence. Source, installed archives
and the actual production bundle each pass the same forty-case native workload.
Three offline consumers pin matching archives. Workspace/diagnostic tests pass
2,647, editor tests 385 and scripts 2,827, with three existing browser opt-in skips.

The first probe incorrectly required an explicit false `readOnly` field, which
the unchanged native format omits. Full before/after view equality replaces that
assumption. Both failed probe runs and the corrected qualification are retained;
this is an assertion correction, not a native-runtime repair.

The earlier snapshot and flat full 480-case source/installed recovery domains
remain mandatory. They carry from the previous checkpoint across verified
unchanged production/package bytes; this read-only slice does not rerun them.
The full candidate plan and Rust suites are not freshly executed.

## Remaining room recovery work

The physical catalog still needs explicit retention/adoption contracts for both
local-operation families in addition to its existing five families. Its old
versions must keep their existing meanings. Actual writer/upload custody,
historical-copy dispositions, complete provider/client reconciliation and newly
authenticated whole-room activation remain required. Native shared Undo and
generation ceilings, full feature parity and all thirteen V1 gates remain open.
