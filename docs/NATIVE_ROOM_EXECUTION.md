# Whole room execution intent

Breditor's private `native_room_execution/` SDK saves the complete replacement
decision before old writers retire or new participants are created. It joins the
existing native preparation, the rebuilt catalog, every destination namespace and
two explicit asset decisions per participant. This stage prepares immutable data;
the mutable executor, its replay journal and authenticated activation remain
separate work.

## Complete replacement inputs

`RoomExecutionArchive.capture` takes a complete preparation file and independent
native read factories. Admission restores temporary read-only native owners,
checks continuity between the complete current and retained cuts, preserves
dependent packets, and rebuilds every concrete participant recipe. The output's
family, selection, length, MIME and digest must match the selected preparation.
A native-valid older participant is insufficient when retained LIVE is newer.
Native history is never rebuilt from the visible AST.

Original, generation, independent-local, independent-delivery, restored-graph and
flat participants keep their concrete output families. Snapshot input explicitly
uses the existing snapshot-to-flat recipe. Complete before and retained files,
literal server and inventory inputs, journals, versions and review packets stay
attached to their established formats. Fresh readers select executable code;
stored metadata cannot select a factory or recover an editing grant.

The layout names the execution intent, catalog, operational root, asset adoption,
approval and every selected upload store. Native participant destinations remain
in the embedded preparation. All roles must be disjoint from each other and the
known complete source namespaces. Duplicate or missing members and cross-role
aliases refuse rather than creating a partial room.

## Three complete asset queues

Each participant contributes its selected current queue, selected retained queue
and rebuilt native output's queue. Native output can carry uploads absent from
both selected queues. Copying only visible image references would lose pending
work.

The first decision reconciles the complete current and retained selected queues.
The second reconciles the actual native output queue with that selected union.
`previewRoomExecutionUnion` reports the first conflicts;
`previewRoomExecutionAdoption` requires their explicit choices before reporting
the second conflicts. Capture requires exact choices for both edges. Neither
epochs, attempt counts nor uploaded status chooses a winner across copies.

Each unchanged reconciled-base frame retains both losing input files as well as
the selected result. Cold admission binds all four full-file edges, both base
digests and the exact native upload queue needed by existing asset adoption.
Pending, failed, cancelled and unreferenced assets retain their bytes and queue
metadata. Local queue decisions are not provider acknowledgements. Archived
limits cannot widen either approved source policy; a fresh host can tighten
admission further without rewriting the archived decision.

## Immutable archive and storage

The new archive starts with `BREDITOR-NATIVE-ROOM-EXECUTION-1\n`, followed by a
little-endian four-byte header length, canonical JSON and contiguous payloads.
Payloads are the complete preparation and two complete reconciled bases for each
member in canonical order. The independent whole-file choice binds every byte,
the rebuilt catalog selection, both source cuts, all destinations and all asset
decisions. Re-pinned headers still undergo semantic native and queue admission;
hashes alone do not establish continuation.

The complete file is limited to 1 GiB, the header to 16 MiB and the cohort to
1,024 members. Embedded complete inputs and losing asset copies consume this
budget. If their aggregate does not fit, preparation refuses without truncating
history or dropping a queue. Existing formats and their limits are unchanged.

`inspectRoomExecution` uses one genuine held source cohort and an existing
preparation. `prepareRoomExecution` independently rebuilds the selected result,
checks the actual current cut, and checks that the intent and every destination
are absent. One upgrade transaction writes one immutable intent record. Full
readback and another current-cut check precede success. No old store is changed
and no replacement participant, catalog or upload destination is created.

An aborted upgrade leaves no empty intent. A lost completion can leave a complete
committed intent; `readRoomExecution` resolves that uncertainty by exact existing-only
read. Repeating creation never overwrites it. Readback checks the schema and
single-row count before loading the large file, then re-admits the complete data.
A missing database aborts its upgrade rather than creating a placeholder. A
successful data read does not recreate source or actor ownership.

## Cancellation and ownership

Read and asset cancellation cover hashing, native factories and raster decoding.
A stopped temporary read does not wait for a stalled host factory. Its late
unclaimed Rust owner is consumed once; an owner already claimed by a genuine
editor remains that editor's cleanup responsibility. Native factory functions
and receivers are detached before authority callbacks can mutate caller options.

Intent resources retain the actual pending IndexedDB request and namespace lease.
Close may report busy while a delayed opening still exists; the same cleanup
handle finishes after the request's real late outcome. A closed phase is not a
substitute for cleanup. Controlled transaction and lifetime tests do not establish
physical power-loss durability.

## Remaining mutable execution

The next boundary must save this exact intent before obtaining fresh retirement
approval, retain the genuine stopped actor cohort through old cleanup, and route
actual actor loans through the [held target route](NATIVE_ACTOR_TARGET_ROUTES.md)
into every concrete staging and final native factory. It must
persist per-target progress, replay interrupted work against real target stores,
adopt each complete selected asset base, admit the complete final root and move
the whole actor cohort synchronously. Cold actor acquisition needs its own
explicit route. No stored stage can skip those checks.

Provider and client reconciliation, independent comment and server generations,
authenticated room activation and sustainable history/asset retention follow
that local executor. A local actor lock is not cross-device author fencing. The
full feature-parity goal and all thirteen V1 release gates remain open.
